## 实施结果

| 范围 | 已完成的行为 |
| --- | --- |
| 账号配置 | 保存真正的旧全局 `n/type/enc` 基线，避免活动账号的高级参数污染其他账号；派生账号不写回内部辅助字段 |

| 多 WAN 认证 | 保留所选逻辑接口、L3 设备与 IPv4 的关联，贯穿初始化、challenge、认证、查询与登出；失败不回退到不受绑定约束的客户端 |
| 严格 DNS | 域名认证和连通性探测使用所选接口的 DNS；缺少可用 DNS 时失败，IP 地址请求无需 DNS |
| DHCP 变化 | 严格请求发送前检查源 IP 仍属于所选设备，拒绝仍被另一设备持有的旧 IP |
| 静默时段 | 纳入活动有线账号、按账号去重，失败后只重试未完成项；混合 Wi-Fi/有线时分别记录完成状态，策略变化和离开窗口后重置 |
| Portal 诊断 | challenge/login 一致区分 HTML、空响应、损坏数据和有效 JSON/JSONP；保留原认证失败，在线复核成功才升级结果；不输出原始响应正文 |
| 动作与 LuCI | 独立保存 `last_action_message` 和认证页入口，后续运行快照不覆盖操作终态；新动作清除旧入口，按钮仅接受当前配置的 HTTP(S) 地址 |
| 连通性缓存 | 区分账号、接口、设备、地址、学校和认证地址，并检查有效期，避免另一账号的在线状态影响本账号引导 |
| 预设与文档 | SWPU 补齐来源、同步 bundled fallback；修正测试环境变量、运行时文件名和 CI 说明，保持 Ruff 版本固定 |
| APK 包互斥 | SDK 实测发现 25.12 的 APK 路径忽略 `CONFLICTS`，现仅在 APK runtime 元数据补负依赖，保持原构建依赖和 IPK 冲突字段 |

## Linux 与隔离双 WAN

在 Linux 开发环境中，以统一 LF 的源码清单核对测试与构建输入。

- Python 3.11.16、Ruff 0.16.5；完整 pytest 为 **326 passed、46 subtests passed**，无跳过。
- shipped Python Ruff、Node JS 语法以及 pytest 内的 Lua 5.1 语法/执行检查通过。
- `scripts/test_network_namespaces.py` 在真实 Linux namespace/socket 上运行，**26 项全部通过**；测试 namespace 均已清理，宿主接口和默认路由保持不变。

| 场景 | 实测结果 |
| --- | --- |
| 两个隔离 WAN 拥有相同 IPv4 | 单纯绑定源 IP 的对照请求走默认 A；严格指定 A/B 分别到达对应 HTTP 服务 |
| HTTP 认证请求出口 | 服务侧记录与指定设备一致，使用虚构测试账号；初始化、challenge、认证和查询/登出的绑定传递另由单元测试覆盖 |
| HTTP 204、Portal 可达与 DNS | 两条线路各自探测，域名解析请求到达对应 WAN DNS |
| 指定线路 DNS 缺失 | 严格域名请求失败，不借用另一线路或全局解析 |
| B 断开、移除 IPv4、删除设备 | B 请求失败，A 持续可用；B 恢复后重新可用 |
| DHCP 从 `.10` 更换为 `.11` | 新请求使用 `.11`；旧事务地址和缓存地址均被拒绝 |
| `.10` 仍属于 A，但 B 已更换地址 | 修复前可错误发送；修复后在发送前失败，服务端未收到请求 |
| 默认路由 | 认证全过程未改写默认路由 |

常用复跑命令：

```sh
python -m pytest tests/ -q
ruff check root/usr/lib/smart_srun/
node --check root/www/luci-static/resources/smart_srun.js
python -m pytest tests/test_lua_syntax.py -v
```

隔离双 WAN 复跑方式（需要 Linux、iproute2、root）：

```sh
sudo python3 scripts/test_network_namespaces.py --output-dir /tmp/smart-srun-netns-check
```

脚本将结果写入指定目录。这些测试验证真实 Linux 发送路径，不代表真实校园网对双账号并发的许可策略。
